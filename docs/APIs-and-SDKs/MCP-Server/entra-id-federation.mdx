# Federated sign-in with Microsoft Entra ID

Your ABsmartly instance's `/mcp` endpoint can accept access tokens issued by
your own Microsoft Entra ID tenant. This lets an application that you run, for
example an internal AI agent, call ABsmartly **on behalf of each of your
users**. Each call acts as the matching ABsmartly user, with exactly that
user's permissions.

Your application gets the token with the Entra
[On-Behalf-Of (OBO) flow](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-on-behalf-of-flow)
and sends it as a `Bearer` token. No ABsmartly API key or browser sign-in is
needed.

:::info Enabled on request
Federated sign-in is off by default. ABsmartly support turns it on for your
instance after you complete the setup on this page and send the
[details we need](#step-4-send-the-details-to-absmartly-support).
:::

## When to use it

| Method | Best for | Who the calls act as |
| --- | --- | --- |
| **Federated Entra ID token** (this page) | Your own backend agent or app that serves many users who are already signed in to Entra ID | The signed-in user, with that user's permissions |
| **[OAuth](./oauth-clients)** | Interactive MCP clients such as Claude, Cursor or VS Code | The person who approved the client in the browser |
| **[API key](./authentication#api-key)** | Scripts, CI/CD and headless agents that act as one account | The account that owns the key |

Use federated sign-in when your application already holds a user's Entra ID
token and you want ABsmartly to apply that user's own permissions, instead of
one shared API key for everyone.

## How it works

1. A user signs in to your application with Entra ID. Your backend receives an
   access token issued for your application.
2. Your backend exchanges that token at Entra ID for a new access token issued
   for ABsmartly (the On-Behalf-Of flow).
3. Your backend calls `https://your-instance.absmartly.com/mcp` with
   `Authorization: Bearer <token>`.
4. ABsmartly verifies the token, finds the matching ABsmartly user and runs the
   MCP request as that user.

## Prerequisites

- **SAML SSO with Entra ID is already set up** for your instance, in the same
  tenant. See [SAML SSO - Azure](/docs/Third-party-integrations/SSO/Azure%20SAML%20Setup).
- **Your users already exist in ABsmartly** and are active. ABsmartly does
  not create users from a federated token. Users usually exist because they
  have signed in to the Web Console with SSO at least once.
- **Your backend application is registered in Entra ID** (or you can register
  it) and can keep a client secret or certificate.
- You can grant **admin consent** in the tenant.

## Step 1: Register an app that represents ABsmartly

This app registration is the "API" that your backend requests tokens for. It
is separate from the enterprise application you created for SAML SSO.

1. Go to the [Microsoft Entra admin center](https://entra.microsoft.com/) and
   head to **Identity** > **Applications** > **App registrations** >
   **New registration**.
2. Name it, for example **ABsmartly MCP**.
3. Under **Supported account types**, choose **Accounts in this
   organizational directory only (Single tenant)**.
4. Leave **Redirect URI** empty and click **Register**.
5. On the **Overview** page, copy the **Application (client) ID** and the
   **Directory (tenant) ID**. You send both to ABsmartly later.

### Set the Application ID URI and expose a scope

6. In the inner left pane, click **Expose an API**.
7. Next to **Application ID URI**, click **Add** and keep the suggested value
   (`api://<application-client-id>`) or enter your own. Click **Save**.
8. Click **+ Add a scope** and fill in:
    - **Scope name**: `mcp.access`
    - **Who can consent?**: **Admins only**
    - **Admin consent display name**: `Access ABsmartly MCP as the signed-in user`
    - **Admin consent description**: `Allows the app to use the ABsmartly MCP server on behalf of the signed-in user.`
    - **State**: **Enabled**

    Click **Add scope**.

<!-- TODO(FT-2378): confirm the scope name ABsmartly configures for /mcp is `mcp.access` (the scope is set per deployment). -->

### Use version 2 access tokens

9. In the inner left pane, click **Manifest**.
10. Under `api`, set `requestedAccessTokenVersion` to `2` and click **Save**.

    ```json
    "api": {
      "requestedAccessTokenVersion": 2
    }
    ```

    If your portal still shows the older manifest format, the same setting is
    the top-level `accessTokenAcceptedVersion` property.

ABsmartly checks the token's issuer exactly. Version 2 tokens are issued by
`https://login.microsoftonline.com/<tenant-id>/v2.0`. Version 1 tokens have a
different issuer (`https://sts.windows.net/<tenant-id>/`) and are rejected.

<!-- TODO(FT-2378): confirm ABsmartly configures the v2 issuer (https://login.microsoftonline.com/<tenant-id>/v2.0) for Entra deployments. -->

### Add the user's email to the access token

ABsmartly matches the token to a user by the **email** claim, the same email
address your SAML setup sends as the Name ID (`user.mail`). Entra ID doesn't
put this claim in access tokens unless you ask for it.

11. In the inner left pane, click **Token configuration**.
12. Click **+ Add optional claim**, choose **Access**, tick **email** and click
    **Add**. If Entra asks to turn on the Microsoft Graph email permission,
    accept.

## Step 2: Give your backend app permission to call ABsmartly

1. In **App registrations**, open the app registration of your backend
   application (or create one with **New registration**).
2. Click **Certificates & secrets** and add a client secret or a certificate,
   if the app doesn't have one yet. Your backend needs it for the OBO request.
3. Click **API permissions** > **+ Add a permission** > **APIs my organization
   uses**, and select the ABsmartly app from Step 1 (for example
   **ABsmartly MCP**).
4. Choose **Delegated permissions**, tick `mcp.access` and click **Add
   permissions**.
5. Click **Grant admin consent for &lt;your tenant&gt;** and confirm. The
   permission's status changes to **Granted**.
6. On the **Overview** page, copy the backend app's **Application (client)
   ID**. ABsmartly only accepts tokens requested by the client IDs you send.

:::tip
You can also pre-authorize your backend app on the ABsmartly app registration:
in **Expose an API** > **Authorized client applications**, add the backend
app's client ID and tick the `mcp.access` scope. Users are then never asked to
consent to it.
:::

## Step 3: Check who can use it

Any user in your tenant that your backend can get a token for can reach
ABsmartly, but only if they also exist and are active in ABsmartly. To limit
this further, open the ABsmartly app's enterprise application (**Identity** >
**Applications** > **Enterprise applications**), set **Assignment required?**
to **Yes** under **Properties**, and assign the users or groups that may use
it under **Users and groups**.

## Step 4: Send the details to ABsmartly support

Send these values to ABsmartly support, for example through your Slack channel
or by email:

| Value | Where to find it |
| --- | --- |
| **Directory (tenant) ID** | Overview page of either app registration |
| **Application ID URI** of the ABsmartly app | **Expose an API** (for example `api://…`) |
| **Application (client) ID** of the ABsmartly app | Overview page of the ABsmartly app |
| **Application (client) ID** of your backend app (one or more) | Overview page of your backend app |
| **Your instance URL** | For example `https://your-instance.absmartly.com` |

None of these values is secret. Never send a client secret or a token.

ABsmartly confirms when federated sign-in is enabled for your instance.

## Request a token with the On-Behalf-Of flow

Your backend exchanges the user's incoming access token (the one issued for
your backend app) for a token issued for ABsmartly:

```http
POST https://login.microsoftonline.com/<tenant-id>/oauth2/v2.0/token
Content-Type: application/x-www-form-urlencoded

grant_type=urn:ietf:params:oauth:grant-type:jwt-bearer
&client_id=<backend-app-client-id>
&client_secret=<backend-app-client-secret>
&assertion=<the user's access token for your backend app>
&scope=api://<absmartly-app-client-id>/mcp.access
&requested_token_use=on_behalf_of
```

Use your own **Application ID URI** in `scope` if you changed it in Step 1.
The `access_token` in the response is the token you send to ABsmartly. It
expires after 60 to 90 minutes, so request a new one when it expires.

The same exchange with
[MSAL for Python](https://learn.microsoft.com/en-us/entra/msal/python/):

```python
import msal

app = msal.ConfidentialClientApplication(
    client_id="<backend-app-client-id>",
    client_credential="<backend-app-client-secret>",
    authority="https://login.microsoftonline.com/<tenant-id>",
)

result = app.acquire_token_on_behalf_of(
    user_assertion=incoming_user_access_token,
    scopes=["api://<absmartly-app-client-id>/mcp.access"],
)

if "access_token" not in result:
    raise RuntimeError(result.get("error_description"))

absmartly_token = result["access_token"]
```

MSAL caches the token and returns the cached one until it is close to expiry,
so you can call `acquire_token_on_behalf_of` before every request.

:::note
Don't send the user's ID token, the token for your own backend app, or a
Microsoft Graph token. ABsmartly only accepts access tokens issued for the
ABsmartly app registration.
:::

## Call `/mcp` with the token

Send the token in the `Authorization` header of every MCP request to your
instance's `/mcp` endpoint (Streamable HTTP). For example, the MCP
`initialize` request:

```bash
curl -i https://your-instance.absmartly.com/mcp \
  -H "Authorization: Bearer $ABSMARTLY_TOKEN" \
  -H "Content-Type: application/json" \
  -H "Accept: application/json, text/event-stream" \
  -d '{
    "jsonrpc": "2.0",
    "id": 1,
    "method": "initialize",
    "params": {
      "protocolVersion": "2025-06-18",
      "capabilities": {},
      "clientInfo": { "name": "my-backend-agent", "version": "1.0.0" }
    }
  }'
```

Most MCP client libraries let you pass custom headers to the Streamable HTTP
transport, so you can set the `Authorization` header there instead.

The `get_auth_status` tool returns the email of the user the call acts as,
which is a quick way to confirm the mapping works.

Federated tokens are accepted on the `/mcp` endpoint only. They don't work on
the hosted server at `mcp.absmartly.com` or on the ABsmartly REST API.

## What ABsmartly checks

ABsmartly accepts a token only when all of these checks pass:

| Check | Token claim | Must be |
| --- | --- | --- |
| Signature | header `kid` | Signed with `RS256` by a current key from your tenant's published signing keys |
| Issuer | `iss` | Exactly your tenant's v2 issuer, `https://login.microsoftonline.com/<tenant-id>/v2.0` |
| Audience | `aud` | The ABsmartly app registration (its client ID or Application ID URI) |
| Tenant | `tid` | Your tenant ID |
| Calling app | `azp` (v2) or `appid` (v1) | One of the backend client IDs you sent to ABsmartly |
| Scope | `scp` or `roles` | Includes `mcp.access` |
| Lifetime | `exp`, `nbf` | Not expired and already valid, with up to 60 seconds of clock skew allowed |
| Token type | | An access token for a signed-in user. ID tokens and app-only tokens are rejected. |
| User | `email` | Matches an active ABsmartly user (not case-sensitive) |

If any check fails, `/mcp` answers `401 Unauthorized`. The response doesn't
say which check failed, so that it gives nothing away to an attacker. Use the
[troubleshooting](#troubleshooting) list below, or ask ABsmartly support to
look up the reason for a specific request time.

The `401` response includes a `WWW-Authenticate` header that points to
ABsmartly's own OAuth sign-in. It is meant for interactive MCP clients. A
backend app using federated tokens should ignore it and fix the token instead.

## Security

- **Your tenant only.** ABsmartly trusts only your tenant's issuer and checks
  the `tid` claim, so tokens from other Entra tenants are rejected.
- **Your apps only.** Only the backend client IDs you sent to ABsmartly can
  use the tokens. Another app in your tenant that was granted the same scope
  is still rejected.
- **Same permissions as the user.** Calls act as the matching ABsmartly user,
  with that user's roles and team permissions. There is no extra access.
- **No credentials can be created.** A federated caller can't create API keys,
  create users, reset passwords or change a password, not even through MCP
  tools. Those actions are refused for federated callers even when the user
  would otherwise be allowed to do them.
- **No new users.** A token for a user who doesn't exist in ABsmartly is
  rejected. Users are never created from a federated token.
- **Revoking access.** Entra ID tokens can't be revoked early. To cut a user
  off, archive the user in ABsmartly (**Settings** > **Users**), which takes
  effect on the next request, and disable or unassign the user in Entra ID so
  no new tokens are issued. Any token already issued stays valid in Entra ID
  until it expires (60 to 90 minutes), but ABsmartly rejects it once the user
  is archived.
- **Keep tokens out of logs.** Treat the token like a password while it is
  valid.

## Troubleshooting

All of these show up as `401 Unauthorized` from `/mcp`.

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| Every request is rejected, `aud` is `00000003-0000-0000-c000-000000000000` or `https://graph.microsoft.com` | The token is a Microsoft Graph token | Request the token with scope `api://<absmartly-app>/mcp.access`, not `User.Read` or `.default` for Graph |
| `aud` is your backend app's client ID | You sent the user's ID token or the token for your backend app | Exchange it with the [OBO flow](#request-a-token-with-the-on-behalf-of-flow) and send the resulting access token |
| `iss` is `https://sts.windows.net/<tenant-id>/` and `ver` is `1.0` | The ABsmartly app issues version 1 tokens | Set `requestedAccessTokenVersion` to `2` in the ABsmartly app's [manifest](#use-version-2-access-tokens), then request a new token |
| `scp` doesn't contain `mcp.access` | The scope wasn't requested, or consent wasn't granted | Request `api://<absmartly-app>/mcp.access` and [grant admin consent](#step-2-give-your-backend-app-permission-to-call-absmartly) |
| The token has no `email` claim | The optional claim isn't configured, or the user has no email address in Entra ID | [Add the email optional claim](#add-the-users-email-to-the-access-token) and check the user's **Email** property |
| The token looks right but is still rejected for one user | No ABsmartly user has that email, or the user is archived | Ask the user to sign in to the Web Console with SSO once, or ask an ABsmartly admin to unarchive them |
| The token is rejected for every user, even with the right claims | `azp` isn't one of the client IDs ABsmartly has, or federated sign-in isn't enabled yet | Compare `azp` with the client IDs you sent to ABsmartly support |
| The token was accepted earlier but now fails | It expired | Request a new token. MSAL does this for you. |
| The OBO request fails with `AADSTS65001` | Admin consent wasn't granted to your backend app | Grant admin consent in **API permissions** |
| The OBO request fails with `AADSTS50013` or `AADSTS50027` | The `assertion` isn't a valid access token for your backend app | Pass the user's access token for your backend app, not an ID token |

To see the claims in a token, decode it with a local JWT tool. Don't paste
production tokens into online decoders.
